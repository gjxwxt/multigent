2. **验证节奏 = 一批次执行完 → 立即 Verification**（不逐提交验证、不跨批验证）：每批次 agent 执行完毕后执行三道闸——(a) **双闸版权验收（v2 修订）**：verify-clean（形式闸：blame 上游行=0）+ **provenance manifest（内容闸：每文件记录来源 commit SHA，与旧仓 bundle diff 审计；重写件附相似度检查）**——外部评审实锤 verify-clean 只读目标仓自身 blame，对新仓（无上游历史）结构上恒真，单独使用检测不了改名式平移；(b) 新仓 `go build ./... && go test ./...` 全绿；(c) 行为等价基线对比（以旧仓测试为基线）。三道闸全过才进下一批次，红了就地修复不带病推进。

## 0. 执行原则（从 v3 红线推导的操作纪律）

1. **验收确定性**：每个批次有机器可验的验收判据（blame 上游行=0 / 测试绿 / 依赖闭包扫描通过），不靠"看着对"。
2. **审计脚本一等公民**：判据纪律（上游行>0 判据 + 依赖闭包必查）固化为 `tools/license-audit/`（见 B1），每次平移后自动跑，脚本红了批次不算完成。
3. **STOP 点显式化**：需要人裁决的地方在批次里标 `⏸ STOP`，执行到点必须停下等输入，绝不自主越过。夜间自主执行只跑无 STOP 点的批次。
4. **批次可回滚**：一个批次 = 一组提交（或新仓一组 commit），失败回滚不连带。
5. **新仓 git 卫生**：新仓从第一个 commit 起作者口径纯净；每批次 tag 可追溯；`git log` 无上游 commit 是永久不变量。
