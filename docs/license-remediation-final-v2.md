### 阶段 2 — 窄接口依赖倒置，攻克 workflow 心脏

**这是全案的技术核心。实测到的三个关键事实：**

1. **`workflow` 已经通过接口依赖持久化**：`store.go:27` 是 `db controldb.Store`（`controldb` = `internal/db` 的别名）。
   好消息是耦合面已经收窄；坏消息是这个**接口定义在上游包里**，搬过去需要重新声明。
2. **`workflow` 的 1,737 行上游残留高度集中**：`store.go` 1,070 行 + `store_test.go` 667 行 —— **全在存储层**。
   ⇒ **替换存储层与清零上游残留是同一件事，一举两得。** 这是本路线最漂亮的一处。
3. **持久化语义是 claim-owner-checked，不是简单 revision 乐观锁**：
   `CommitTransitionGuarded`（`db/workspaces.go:523`，67 行）与 `...Tx`（:590，58 行）
   是**事务性、claim 持有者校验的批量提交**——语义接近租约 / fencing token，不是
   `UPDATE ... WHERE revision = ?` 能覆盖的。

**动作**：
1. 新仓定义**窄接口** `RunRepository`（只声明 workflow 实际用到的语义，**不复制 `db.Store` 的 20+ 个方法签名**——复制签名集合本身有风险，窄接口在法律上也更安全）
2. 实现 SQLite 版本：**claim 语义 + 事务批量写 + Tx 变体**，函数体参照 125 行，但需自建底层 KV/claim 存储
3. 接入 `workflow`（15,418 行自有），把 `store.go` 中对上游存储的调用全部改到新接口
4. 清零 `store.go` / `store_test.go` 的 1,737 行上游残留

**工作量修正**：主张"300–500 行"**低估**。真实成本不在函数体（125 行），而在：
① 底层 KV + claim 存储 ② **并发/过期/重入的边界测试**（这是最容易出 bug 的地方，原仓有专门测试）
⇒ 估算：**接口 200 行 + 实现 800–1,200 行 + 测试 1,200–1,800 行 ≈ 2,200–3,200 行**

**验收判据**：workflow 包 blame 上游行 = 0；原仓 `transition_idempotency_test.go` 等幂测试在新仓全绿。

### 阶段 3 — 裁剪后的 API + 实时通道 + 前端

**实测的功能面**（这两个数字决定裁剪代价）：

- 现有注册路由端点 **475 个**
- **前端实际调用 130 个不同的 `/api/v1/*` 端点**
- 另有 **WebSocket 实时通道**（`internal/api/agent_channel_ws.go` + `agent_channel_events.go` 2,854 上游/600 自有）

**主张"只需 40–45 个端点"的两处遗漏**：
1. 从 130 砍到 45 = **砍掉 65% 的现有功能面**。这不是后端的事，是整个产品范围的事，必须逐端点过一遍再定。
2. **未计入 WebSocket**。人机协作 Agent 平台的实时通信不是 REST 端点，且它恰是上游代码最集中的区域之一。

**动作**：
1. 出**端点级裁剪清单**：130 个逐一标注 保留 / 延后 / 废弃（这一步不能跳，否则功能裁剪就是口头砍）
2. 后端：保留端点 × 现代 Go 实现 + auth/RBAC/审计中间件 + WebSocket 通道
3. 前端：见下方 ☛ 前端资产回收账本。⚠️ 前端是**对外可见面**，是 (2025)川知民终 90 号下最容易被比对取证的靶子，**优先级不低于后端**

#### ☛ 前端资产回收账本（逐文件 blame 后，"整仓弃写"的代价远小于直觉）

`web/src` 自有 **16,138 行**。逐文件审计后分三档：

| 档 | 文件数 | 自有行 | 处置 |
|---|---:|---:|---|
| **纯自有**（上游行 = 0） | 36 | **9,156** | ✅ **直接平移**，零法律问题 |
| 高自有混同（自有 >80%） | 9 | 4,152 | ⚠️ 逐行 blame 后剥离上游行，**部分回收** |
| 其余混同 | — | **2,830** | ❌ 弃置（这才是真实的弃置成本） |

> **修正一处直觉**：有意见认为前端 31% 自有行（约 1.6 万行）需整体计入弃置成本。
> **实测远没那么糟**——文件级 blame 后**只有约 2,830 行真正需要弃置**，可回收 13,308 行。
> 代表：`PreviewDrawer.tsx`(2,253 纯) · `CreateProjectDialog.tsx`(905 纯) ·
> `DeliveryPlanAcceptanceTable.tsx`(393 纯) · `DeliveryPlanEditor.tsx`(331 纯) ·
> `DesignReviewModal.tsx`(308 纯) · `deploy/*`(全部纯自有)。

**整仓弃写在法律上是对的（混同即衍生），但"弃"必须是审计后的选择性弃，不是一刀切。**

**工作量**：保留端点约 6,000–8,000 行 + 基础设施/WS 约 4,000 行 + 前端净新写约 10,000 行 ≈ **20,000–22,000 行**
（前端 10,000 行是"要做的目标形态"，不是"要放弃的自有资产"——自有资产另有 13,308 行可平移/回收）

### §4.5 三个被前序方案整体漏掉的东西

#### ① 生产数据库 schema 与存量数据——**最尖锐的一个**

可行目录下存在生产库（`.multigent/multigent.db`、`.multigent/control.db`）。

**问题**：阶段 2 的核心是"抛弃上游 `entity` 的冗余字段、重新定义领域模型"。
**这等价于改变 schema ⇒ 存量数据进不了新仓。**

必须二选一并**现在就决策**，不能拖到切换时才发现：
- **写迁移器**：从旧 schema 抽取 ⟶ 映射到新 domain model（工作量取决于保留字段的重合度）
- **明说"新仓不带历史"**：新仓从空库起步，旧库只作归档查询

> 这条不等价配置托底的推论：**如果你要保住正在跑的业务（ias-auth-center、RoomFlow）的状态数据，
> 迁移器就不是可选项。** 请在阶段 2 动工前先定。

#### ② 模板资产未做 blame

`internal/projecttemplate` 的 `.json` / `.yaml` 模板文件**不在代码 blame 覆盖范围内**（初版脚本只统计源码后缀）。
它被列入了 A 组，但**该结论尚不成立**。新仓平移前必须单独盘一遍模板资产归属。

#### ③ 法务角色缺位

本底稿开篇即声明"**不是法律意见，正式决策需法务确认**"。
任何把本方案当执行计划落地的版本，都必须把**法务确认**作为一个显式步骤写进去，而不是脚注。
尤其是 §2-R3（内部业务系统是否构成 commercial advantage）——这一条的判断权不在我。

#### ④ 事实基准漂移

## §6 授权决策：算，不要站队

| 项 | 数值 |
|---|---|
| 自研成本 | 20,000–28,000 行新代码，工期以月计 |
| 授权成本 | 估 $1,000–10,000（一次性）或 $1,000–5,000/年 |
| **询价成本** | **一封邮件，≈ 0** |

**决策规则（建议）**：
- 若报价 ≤ 自研总投入的 10%（按你的工时成本折算），**买**——它同时覆盖过渡期风险，且省下几个月
- 若报价离谱（> $50k），**不买**，走自研
- **无论结论如何，询价都该做**——它的成本是零，而你目前连报价都不知道

**"坚决一分钱不给"是把手段当成了目的。** 你要的是自主可控，省钱只是副产品。
如果 1,000 美元能买几个月的合法窗口，那它不是"过路费"，是**最便宜的时间**。
