## 3. 逐页价值分析要点（P0 内部排序说明）

1. **任务链路 > 工作流设计**：工作流是"配一次"，任务是"天天跑"——同一优先级下任务链路先验收。
2. **连接 > 设置**：连不上 GitLab/MM 什么都跑不了；设置里 Provider 是唯一硬依赖，其余设置项可分步。
3. **知识库价值在"内容沉淀"**：docs 树 + knowledge-base 双面都要，内网知识（规范/拓扑/公共账号位）是团队协作的独有资产。
4. **部署中心是验收出口**：近期每一轮功能交付的最终证据都出自这里（部署单→审批→健康卡→访问应用），断裂则验收链断裂。
5. **智能体页含两个子面**：全局 agent workers + 项目 agent 配置，后者与任务链路耦合更深，先做后者。

## 4. 消息页面专题（用户委托探索，结论待审）

### 4.1 实测证据（VM 生产实例，2026-10-07）

| 事实 | 数字 | 含义 |
|---|---|---|
| 消息总量（kv_records/messages） | **40,042 条** | 看起来是"高频功能" |
| 其中 `heartbeat:wakeup` 收件 | **39,047（97.5%）** | 全部是 agent 间心跳唤醒**机器信令**，人永远不看 |
| 人/agent 真实邮箱消息 | **~584 条（1.5%）** | admin 220、agent 邮箱 288、gaojiaxiang2018 39、human 37 等 |
| attention_signals | 592 条，task 308 / message 265 / im 19 | 人真正消费的"需要处理"信号走 attention，不走消息页 |
| attention 原因分布 | workflow_step_assigned 164 / task_assigned 144 / inbox_message 265 | 人工审核指派+任务指派是"待我处理"的主体 |

### 4.2 结论

**现有项目消息页面是一个"伪高频"页面**：数据量大是因为 agent 心跳信令灌进同一张表；人读的部分（1.5%）真正的消费入口实际是 attention 信号、任务评论和 Mattermost。复刻这个页面到新仓 = 把一条机器管道的 UI 壳搬过去。

### 4.3 重新设计方向（P1，出方案再审）

新仓**不做独立消息中心**，改为两件事：

1. **待办中心（Attention Inbox）**：聚合"需要人处理"的信号——人工审核指派、任务指派、IM @、agent 挂起告警。数据源就是 attention_signals（它在 P0 底座里天然保留），按状态（pending/seen/handled）+ 来源过滤，点击直达对应任务/工作流节点。
2. **机器信令下沉为管道**：heartbeat:wakeup 类消息不再有 UI 面，退化为内部机制（新仓 D 批窄接口自然吸收）。

原 messages 域的"人发消息给 agent 邮箱"能力（220+ 条 admin 使用）收敛为任务评论 + @ 引用资料，不再保留独立站内信。

### 4.4 需要用户确认的一点

- 站内信"人→agent 邮箱"发送（现有 CreateMessageDialog）在新仓是否还需要？实测中 admin 发过 220 条，若这批消息本质是"派活指令"，任务评论/任务创建就能覆盖 → 建议砍；若你真用它做独立沟通 → 保留为 P1 待办中心的输入框。
