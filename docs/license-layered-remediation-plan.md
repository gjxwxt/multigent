### G1 与 G2 是**两个不同的目标**，最优路线不同，必须先排序

这点很关键，混在一起会得出错误结论：

| | 目标 G1「能商用」 | 目标 G2「成为自己的项目」 |
|---|---|---|
| 最短路径 | **买授权**：$1k–10k，工期 0 | **重写**：15 万行，工期以年计 |
| 买授权够不够？ | ✅ 够了 | ❌ 不够——买了授权它仍是"上游的项目的授权版" |
| 重写是不是必需？ | ❌ 不是，是浪费 | ✅ 是唯一路径 |

**所以**：如果你的首要目标是"尽快商用"，答案是买授权，不是重写 15 万行；
如果首要目标是"成为自己的项目"，那重写是必须的，但**商用窗口要等**，不能因为重写进度过半就提前开门。
**本方案默认你两者都要**，因此走双轨（§7）；但你必须知道自己把哪个排第一 —— 这决定资源怎么投。

## §2 三条不可绕过的法律事实（P0，先钉死）

### F1 — PolyForm 限制的是「使用行为」本身，不是「分发衍生作品」

本地 `LICENSE` 原文：

> You may use, copy, modify, and distribute this software **only for noncommercial purposes** as permitted by the license.

**`use` 也在受限之列。** 这跟 GPL 家族完全不同——GPL 是"分发衍生作品才触发 copyleft"，
PolyForm 是"你只要用了这段代码去换取商业优势，就违约"。

**推论（这条最容易被想错）**：
❌ **"把上游代码隔离成独立微服务 / 独立进程，通过 API 调用" —— 无效。**
使用行为本身受限，进程边界救不了你。LGPL 那套"动态链接豁免"的思路在这里完全不适用。
（顺带：PolyForm Noncommercial 的 noncommercial 定义为 "not primarily intended for or directed toward
commercial advantage or monetary compensation"，**连企业内部自用也堵死了**——"不外卖就不算商用"不成立。）

### F2 — 合法出路只有两条，没有第三条

1. **拿到书面商业授权**（上游 README 明写有此通道："without a separate written commercial license from the copyright holder"）
2. **让代码库里不再存在上游代码** —— 删、换、重写，三者之一

**"改了很多所以算我的"不是一条出路。** 修改量是谈判筹码，不是法律上的重新授权理由。

> **但"两条出路"讲的是合法性，不是风险暴露** —— 这两件事必须分开看：
> 合规是二值的（合法 / 违法），**风险暴露是梯度的**（会不会被发现、被谁发现、赔多少）。
> 本方案不主张"没被抓到就没事"；梯度只用于决定**清理的先后顺序和商用窗口的开启时机**，
> 不用于判断"这样做行不行"。

### F4 — 中国司法实践：**不存在"PolyForm 无判例所以风险低"这回事**

有人主张"PolyForm 在中国无判例体系，所以风险是梯度、可以先商用"。**前提是事实，推论是错的。**
中国法院不需要"PolyForm 特定判例"——用的是**一般著作权法 + 合同法的成熟框架**，且**已有直接判例**：

| 案号 / 法院 | 要点 | 结果 |
|---|---|---|
| **广州知识产权法院**（最高法知产法庭典型案例） | 被告"收取会员费"的行为**违反限制商业使用条款**及 GPL V3，授权自动终止 | **判赔 50 万元** + 停止提供下载/安装/运营服务（原告诉请 1500 万） |
| **(2021)最高法知民终 51 号** | 开源软件的衍生作品同样受著作权保护；违反开源协议 ≠ 可以抗辩不侵权 | 判赔 50 万元，维持原判 |
| **(2025)川知民终 90 号 / (2024)川 01 知民初 184 号** | **无需取得源代码**：只要证明被诉软件"运行时显示的信息"与权利软件高度一致，被诉方无法合理解释的，**法院可推定实质相似** | 确立裁判规则 |
| **(2024)苏民终 581 号** | 开源协议影响侵权认定与赔偿数额的考量 | 最高法年度报告收录 |

**最高法定性**：开源协议 = **附解除条件的著作权许可使用合同**；违反许可条件 → **授权自动终止** → 继续使用即构成侵权。

**推论（打掉两个常见幻想）**：
1. ❌ "没有 PolyForm 判例所以安全" —— 广州案就是**"违反商业使用限制"**的直接判例，性质高度相近。
2. ❌ "把上游代码隔离进内部服务，对方举证更难" —— 川知民终 90 号明确：**看运行时表现就能推定实质相似，不需要拿到你的源代码**。进程边界降低的是工程摩擦，不是举证难度。

### F3 — 看过原作，就丧失了"独立创作"抗辩

你（以及看过上游代码的人）亲自重写，在法律上叫**翻译式重写**，100% 构成衍生作品，是最危险的做法。
真正的 clean room 要求"实现者从未接触过原代码"。你一个人做不到。
**本方案能做到的最强形态是"需求驱动重写"**（§6），它比 clean room 弱，但比翻译式重写强得多，且能留下证据链。

### P0 的三件事（今天就能做完，唯一零风险阶段）

1. **停止同步上游**：每同步一次，污染面扩大一次。已确认：HEAD 含 `bda6e888`（PolyForm 切换点）。
2. **快照存证**：把当前 HEAD 完整归档（含 git 历史）到独立位置，作为"改造起点"的证据，防止后续被质疑。
3. **发授权询价信**（`chg80333@gmail.com`）——**这条线不能断**，见 §7。

### 两条贯穿全程的工程纪律

**纪律 A｜单向依赖原则（零成本，立即生效）**
从今天起，所有新代码写在**新的自有包**里。允许"新包 → 旧包"单向依赖，**禁止反向**。
这样时间会自动站在你这边：占比随新功能增长而自然下降，且未来替换旧包时只改适配层。

**纪律 B｜防腐层（Anti-Corruption Layer）**
在自有核心（`workflow` 等 L0）与上游孤岛之间加显式适配接口。
好处有二：① 把上游代码压缩到边界内，缩小重写面；② 未来替换时只改适配层，上层不动。

## §6 重写纪律（"需求驱动重写"，clean room 的可操作版本）

做不到真 clean room（§2-F3），但下面六条能把你推向"独立创作"那一侧，并留下证据。

| # | 纪律 | 具体要求 |
|---|---|---|
| **R1** | **从运行时行为取材，不从代码取材** | 想知道某模块做什么，就**把系统跑起来看它的行为**，或读你自己写的需求文档；**禁止打开上游源码对照** |
| **R2** | **命名与结构从行业标准出发** | 想到 workflow 引擎，脑子里应该是 DAG / retry policy / trigger_rule / semaphore（Temporal、Argo、Airflow 的公开概念），**不是** `PlanWaves` / `EvaluatePlanProgress` / `PlanWPStateDeferred` |
| **R3** | **每个重写模块留一份《设计说明》** | 内容：需求是什么 → 有哪几种设计选项 → 为什么选这个 → 放弃了什么。**这是"独立创作"最直接的证据** |
| **R4** | **禁止 diff 对照式移植** | "照着它改成我的写法"= 翻译式重写 = 最危险。写完不看原文件 |
| **R5** | **用行为等价验收，不用代码相似度验收** | 旧系统的行为录成 golden 测试，新实现通过同等验收才算替换完成 |
| **R6** | **优先用干净第三方替代自建** | 能换就换，见下 |

## §7 商业授权：不能放弃的并行线

分层处置是 B 计划，**买授权才是 A 计划**。理由很简单：P3–P7 涉及约 15 万行重写，
按业界"等价功能重写 = 原工作量 1.5–3 倍"的经验，这是一次**大规模工程**，不是顺手的事。

**市场参照（PolyForm 自身无定价，定价权在版权方）**：

| 参照 | 模式 | 数字 |
|---|---|---|
| AG Grid Enterprise | 席位年订阅 | $995–1,295/开发者/年（单应用）；$1,495–1,995（多应用） |
| 永久授权惯例 | 买断 | ≈ 年费 **2–3 倍**；年度维护约 20% |
| 中小 source-available 项目 | 一次性买断 | $300–$5,000 |
| 本项目的现实区间 | — | **一次性 $1,000–$10,000** 或 **年费 $1,000–$5,000**（估） |

**开局一句话问清三件事**：① 是否有商业授权；② 定价模式（买断 / 年费 / 按部署实例）；
③ 授权范围（能否修改 / 能否闭源 / 能否 SaaS 转售）。

**筹码**：541 个提交 + 完整的机制设计（DeliveryPlan 物化、设计闸门、预览引擎租期、CI 基线、六条安全红线）
对上游同样有价值，可谈"回贡献 + 付费"组合。

⚠️ **授权只对特定快照有效** —— 谈成之后依然不能同步上游新代码，否则新代码不在授权范围。

| **A3** | HEAD 可达集合内的上游 commit 数 | **728** | **0** |
| **A4** | 核心模块是否有《设计说明》证据链 | 部分 | **100%** |
| **A5** | 依赖树是否存在 copyleft | 无（已核实） | 持续门禁 |

> ⚠️ **A1 是"工程进度指标"，不是"商用安全门槛"。**
> 法律不看比例——**49% 自有和 60% 自有，在侵权认定上没有任何区别**。
> 任何"自有比例到 X% 就可以上商用"的说法都是**虚假安全感**：60% 自有意味着还有 40% 上游代码在跑，
> 而这 40% 里只要有一段出事，就是全案出事。
> A1 用来衡量清理进度；**能不能商用，只看一件事：你要交付的那个功能链路上，还有没有上游代码。**

### A3 是最容易被漏掉、也最致命的一条

你现在 1271 个 commit 里有 **728 个是上游的**。
**即使你把代码 100% 重写了，只要 git 历史里还留着这些 commit、且仓库 fork 自上游，
对方举证的难度接近于零。**

**收尾动作（P7 之后）**：新建空白仓库，只提交自有代码快照 + 自有历史，**不带上游 commit**。
这是唯一能让 A3 = 0 的做法。

## §10 「净室萃取」路径的可行性实测

> 有人提议：新开干净仓库，只平移自有核心（workflow / gitworktree / preview / ciready），
> 外围用 3–5 万行新代码重写，绕开 §5 的 P3–P7。**方向值得采纳，但前提必须先测。**

### §10.1 实测：「心脏」能不能直接搬走？

按"是否 import 上游包（上游占比 >60% 的包）"把自有代码分两组：

| 组 | 判据 | 自有行 | 能否直接平移 |
|---|---|---:|---|
| **A 组** | 零上游依赖 | **21,044**<br>（含 `imbridge` 的 3,713 行残留则为 26,614） | ✅ 可以 |
| **B 组** | 依赖上游包 | **107,780** | ❌ 必须先解耦 |

**A 组明细**：`previewreceipt` 5,243 · `gitworktree` 3,794 · `fixturesandbox` 2,490 · `changerun` 2,257 ·
`codehost` 2,136 · `projecttemplate` 1,421 · `brownfield` 1,107 · `doctor` 865 · `ciready` 815 ·
`assets` 509 · `secretbox` 407 —— **全部零上游残留，可以立刻搬进新仓**。

**B 组（搬不走的）**：`api` 73,722 · **`workflow` 15,418** · `db` 8,697 · `runner` 4,455 ·
`preview` 1,975 · `sandbox` 1,751 · `taskstore` 1,589 …

> ⚠️ **关键推翻**：被称作"心脏"的 **`internal/workflow` 在 B 组**，不在 A 组。
> 它 import `entity`（64% 上游）和 `errs`（100% 上游）；`db`（5,691 行上游）又依赖 `connector`（87% 上游）。
> 主张"只看核心模块的话依赖项其实很收敛"——**恰恰相反，依赖收敛在最难的两个包上**。
> 可平移量是 **2.1 万行，不是 6–8 万行（差约 3 倍）**。

### §10.2 实测：API 层重写要多少行？

主张"5,000–8,000 行取代 60,000 行"。实测：

- 现有注册路由端点 **475 个** → 60,086 上游行 ÷ 475 ≈ **126 行/端点**
- 即便功能砍到 1/5（≈100 个端点），重写量 ≈ 12,600 行
- **加上省不掉的部分**（auth / 中间件 / RBAC / 错误处理 / 序列化），实为 **15,000–18,000 行**
- 软件工程常态是"功能砍半、代码只砍 30–40%"，不是线性缩减

→ **比主张值高一倍。**

### §10.3 但这条路径有一个**真实且重要**的优势，本方案采纳

**同样是"重新定义 `entity`"，在新仓做远比在旧仓做便宜**：

| | 在旧仓重写 entity | 在新仓重写 entity |
|---|---|---|
| 需要同时改的调用点 | **314 个文件** | 只需满足少数消费者（workflow 等） |
| 回归风险 | 全仓 | 局限于新仓 |

**这是一个数量级的差别。** 所以 §5 的 P3（entity/store/db 置换）**应当挪到新仓里执行**，
而不是在旧仓里"给危房换地基"。**据此修正 P3–P7 的执行方式**：

| 原方案 | 修正后 |
|---|---|
| P0–P2 在旧仓摘孤岛，P7 才建新仓 | **P0 立即建新仓**，先把 A 组 21,044 行搬进去 |
| P3 在旧仓置换 entity/db（改 314 处） | **在新仓重新定义领域模型**，只服务被搬入的模块 |
| P5/P6 在旧仓重写 API/前端 | **在新仓按裁剪后的功能清单写**，旧仓保持冻结只读 |

### §10.4 三条不能接受的主张

| 主张 | 为什么不能接受 |
|---|---|
| **"Day 1 达成法律合规"** | 假的。搬过去的 `workflow` 自带 **1,737 行上游残留**、`imbridge` 自带 3,713 行。Day 1 只是"建仓"，不是"合规" |
| **"不要买授权"** | 新仓从建立到可用需要数月。这段时间里**现有系统仍有 50.8% 上游代码**，若商用即裸奔。授权是**过渡保险**，与这条路径不冲突——它不是"过路费" |
| **"只需支撑 5 个核心链路"** | 未对应到端点清单就下结论。475 个端点是客观功能面，裁剪必须先出**端点级裁剪清单**，不能口头砍 |

### §10.5 还缺的一环：业务连续性

现有系统在生产运行。新仓功能若不对等，**业务会中断**。
动工前必须先产出：**① 端点级裁剪清单（保留/废弃逐一标注）② 行为等价测试基线 ③ 双轨切换方案**。
这三项不做，路径三就是"推倒重来 + 业务中断"的另一种说法。
