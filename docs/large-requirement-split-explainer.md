## 0. 一句话版本

**模型提议拆分，人来拍板冻结，引擎机械执行；执行中每个工作包都是独立的 git worktree + 子任务，失败不静默、挂起有告警、放弃要留痕。**

## 1. 为什么需要这套东西（问题定义）

### 1.1 没有它时会发生什么

把一个几千行的大需求（比如一份军标式 SRS）直接丢给一个 Agent，会撞上四堵墙：

1. **上下文墙**：单个 Agent 的上下文装不下"全部需求 + 全部代码 + 全部改动"。
2. **串行墙**：一个 Agent 依次做 10 个功能，总时长 = 10 个功能之和。
3. **信任墙**：你说"做完了"，没人能机械地验证你真的做完了你负责的那部分。
4. **混沌墙**：多个 Agent 直接在同一个目录里各改各的，互相覆盖。

### 1.2 这套设计给出的答案（先剧透）

| 墙 | 答案 | 机制名 |
|---|---|---|
| 上下文墙 | 大需求拆成 N 个工作包，每个 Agent 只看自己的包 + 一份共享契约 | scale_gate + 交付计划 |
| 串行墙 | 无依赖的包并行跑，有依赖的按波次解锁 | parallel_stage + 波次物化 |
| 信任墙 | 每个包有验收锚点（引用需求条目 ID），机器可查 | requirement_items + QA 基线 |
| 混沌墙 | 每个包独立的 worktree（隔离的工作副本），互不可见 | 1:1:1:1 不变量 |

**★ 标记的两个节点是整个设计的枢纽**：scale_gate 决定"拆不拆"，contract_review 决定"按什么拆"。

## 3. 核心数据结构：交付计划（DeliveryPlan）

这是整个系统里最重要的一份"合同"。通俗地说，它回答四个问题：

```json
{
  "schemaVersion": 1,
  "planId": "plan-acceptance-round3-four-independent-features",
  "requirementItems": [
    {"id": "req-1", "text": "登录页增加记住我，勾选后 token 有效期 7 天", "source": "验收计划 第1条"}
  ],
  "workPackages": [
    {
      "id": "wp-1",
      "title": "登录页记住我 + 7 天 token",
      "dependsOn": [],
      "acceptanceCriteria": ["req-1"],
      "agentBinding": "FP Dev A"
    },
    {
      "id": "wp-3",
      "title": "审计日志 CSV 导出",
      "dependsOn": ["wp-1"],
      "acceptanceCriteria": ["req-3"],
      "agentBinding": "FP Dev C"
    }
  ],
  "integrationPolicy": "feature-branch-merge-to-main",
  "qaPolicy": "..."
}
```

1. **需求条目快照（requirementItems）**：把需求拆成编号的锚点（req-1、req-2…）。**快照**是关键词——人批准计划的那一刻，这份清单被拍死进冻结记录。之后就算上游把需求文本改了，锚点也不动。这防止"需求悄悄变了，但验收标准还指着旧的"。
2. **工作包（workPackages）**：每个包 = 一件能独立交付的事。必须有：
   - `dependsOn`：先完成谁（只影响顺序，见 §6.3）；
   - `acceptanceCriteria`：引用 req-N 或 `infra:xxx`（基础设施包豁免需求关联，但豁免的只是"关联"，不是其他任何纪律）；
   - `agentBinding`：哪个 Agent 干（**校验只要求非空**——agentBinding 与 actorRole 至少填一个，否则拒绝；绑定值能否解析到真实 Agent 不在冻结期校验，解析失败会在派发时暴露并留 attention，见 §8 问题 3）。
3. **波次（wave）由 dependsOn 自动推导**：无依赖 = wave 0；依赖 wave 0 = wave 1。人不用手排顺序。
4. **摘要指纹（digest）**：冻结时对计划全文算 SHA-256。之后每次读取都验指纹——**存储里一个字节的篡改都会被拒绝，而不是被默默接受**。

### 3.1 信任模型（这段是给审查者最重要的背景）

计划是一份**控制面产物**，它的信任来源链条是：

```
Agent 起草（不可信）
  → 人审批准（信任的注入点，全系统只有这一个）
    → 冻结记录 + digest（写进同一个数据库事务）
      → 运行时只从"指纹验证通过的冻结记录"读取
```

三条铁律（`internal/workflow/plan.go` 头注原文意译）：
- **物化时永远不从"Agent 的散文、运行输入或画布状态"派生任何东西**——只从冻结记录读。
- digest 覆盖一切实质字段（需求快照、工作包、依赖、验收引用、绑定、策略）。
- Agent 报告"我做完了"永远不等于"做完了"——完成状态以分支实例的状态机为准。

## 4. 数据流转全程（一份需求的一生）

### 第 1 站：向导预拆分（可选加速，不落库）

```
人贴需求 → POST /delivery/preplan → LLM 一次性调用 → 返回草案 + scaleHint
```

- **无状态**：这个端点什么都不写。草案只活在浏览器里，人可以随便改。
- 为什么不直接落库？因为正式裁决是流程里的 scale_gate，落库会造成"两份计划谁说了算"的歧义。草案的角色是**让操作者在任务创建前就能看到并修正拆分**——省掉"发起后中段才发现拆得不好"的返工。
- 输入上限 512KB（覆盖 156KB 军标 SRS），资料库文件最多 4 份/次。

### 第 2 站：scale_gate 裁决（流程内，正式）

Agent 读完全部输入后输出结构化裁决 `scale_verdict`：
- `linear`（一个 Agent 顺序做就行）→ 跳过并行场，走老路径；
- `batched`（必须拆）→ 进入契约批。

**兜底设计**：如果 Agent 没输出裁决（跑了、但没交卷），默认边把流程引向 linear——宁可降级串行，也不瞎拆。

### 第 3 站：contract_batch 共享契约批（拆分质量的第一次人机博弈）

Agent 做两件事：
1. **把共享地基先建好**：数据库 schema、错误码、API 骨架提交成一个 commit（基线 SHA）。为什么？因为并行分支互相看不见对方的代码，这份契约是它们唯一的共享面。契约先行 = 并行时不吵架。
2. **重发计划**：把 scale_gate 的计划（可能加了修订）作为输出重新提交。系统规定"只停留在输入侧的计划永远不会到达人审"——输出副本才是评审对象，防止"Agent 说看了，其实没传"。

### 第 4 站：contract_review 契约评审（★ 全系统唯一的信任注入点）

人看到：契约内容 + 结构化计划 + 需求锚点。点"批准"的那一个数据库事务里：

```
事务开始
  校验计划可解析、合法（fail-closed：模板承诺给人看计划，实例输入里却没有 → 拒绝批准）
  钉入 RunID → 算 digest → 写冻结记录
  工作流推进到 parallel_workstreams
事务提交（两件事同生共死：计划没冻上 = 流程不前进）
```

这就是为什么说"**批准即冻结**"——不存在"批了但计划还没写进去"的中间态。

### 第 5 站：parallel_workstreams 并行场（引擎执行，零 LLM 参与）

这是最机械、也最讲究的一站。每一次推进都执行同样的循环：

```
读取冻结计划 → 算每个 WP 的当前状态 → 找出"就绪"的包（依赖全部 completed 且自己没实例）
  → 按并发闸截断（默认同时最多 2 个在飞）
  → 每个就绪包物化：1 个子任务 + 1 个分支实例 + 1 个 git worktree + 1 份 QA 基线
  → 派发给 agentBinding 指定的 Agent
  → 有包完成？解锁它依赖的包（波次 k+1 自动补位）→ 回到开头
```

**1:1:1:1 不变量**：一个工作包 ↔ 一个子任务 ↔ 一个分支实例 ↔ 一个 worktree ↔ 一份 QA 基线记录。重跑、补位、崩溃恢复都不得产生第二套身份（幂等键 `plan/<runID>/<planVersion>/<wpID>` 保证，`plan_materialization.go:266`）。

**并发闸（P0-1）**：`MULTIGENT_PLAN_MAX_PARALLEL` 默认 2。为什么要限？N 个 Agent = N 个容器 + N 份内存，不设上限的扇出能把宿主机打爆。被闸住的包不丢——留在"就绪"桶里，任何一次分支完成都会触发重新物化。

### 第 6 站：join 集成（全部包终结后）

所有包到达终态（completed / deferred）→ join 放行 → 集成评审（人）→ 后续 17 步流程继续。

## 5. 失败处理哲学：三种终局，三种待遇

一个工作包失败了，只有三种合法出路——**每一条都要人来拍板，系统绝不自作主张**：

| 出路 | 语义 | 对流程的影响 | 留痕 |
|---|---|---|---|
| **retry 重试** | "再试一次，可能是偶发" | 同一个子任务复活（身份复用，绝不重物化）；每个包最多 2 次 | 重试预算记在分支实例上，超限返回 409 并提示改用 defer |
| **defer 缓办** | "这轮不做，下轮再说"（人的终审裁决） | 包标记 deferred，**不再挡路**；它的下游依赖自动传染成 deferred；可选自动建一个待办任务回流 | 失败摘要原样保留（"deferred; original failure: …"），失败类别（compile_test/business_assertion/environment/unknown）记档 |
| **blocked 阻塞** | "上游失败把我堵死了" | 流程停住，阻塞链**显式可见**——失败永远不能看起来像"没事可做" | 根任务上写明阻塞原因 |

**为什么 defer 不挡路而 failed 挡路？** 语义差异：failed = "尝试了但没做成，问题还没解决"；deferred = "人审过，决定这轮不做"——问题被处置了，只是处置方式是移出本轮。两者的信用等级不同，所以 join 对它们的待遇不同。

**重试为什么复用身份而不重新物化？** 因为重新物化 = 新的子任务 = 前一次失败的现场全丢。复用身份让"第几次重试、为什么失败、改了什么"保持在同一条审计线上。

## 6. 重要设计决策及其理由（审查重点区）

### 6.1 为什么 scale_gate 在设计确认之后，而不是之前？

直觉上应该先判断规模再设计。现实相反：**大设计本身可能白做**（如果最后拆成 batched，每个包的设计都重新框定），所以顺序是"需求 → 设计 → 裁决"。裁决需要的输入里包含设计结论。

### 6.2 为什么计划冻结挂在 contract_review，而不是单独一个"冻结按钮"？

- 单独按钮 = 新增一个信任注入点 = 新增一种"批了 A 冻了 B"的不一致可能。
- 挂在评审上，冻结和流程推进在**同一个数据库事务**里，结构性消灭了不一致。
- 副作用是语义耦合："批准契约"和"批准计划"变成同一个动作。我们接受这个耦合，因为在这个流程里它们本来就该同时成立。

### 6.3 为什么 dependsOn 只管顺序，不管 join？

规则原文："Dependencies affect ORDER only."（依赖只影响顺序。）

- 一个包依赖失败的上游 → 它被传染成 blocked（挡路，显式暴露）；
- 一个包依赖被 defer 的上游 → 它被传染成 deferred（不挡路）；
- 但 join 等的是"所有包终结"，不是"依赖图闭合"。

传染是**每次评估时从 DAG 确定性重算的**，不存储、不需要手工级联——人 defer 一个包，下游自动跟着变，没有"忘了通知下游"这种 bug 的生存空间。

### 6.4 为什么物化引擎零 LLM？

并行的派生（哪些包就绪、开几个分支、绑给谁）全是纯函数计算。LLM 在这条链路上**没有任何 Writes**：它起草计划（第 1 站）、产出裁决（第 2 站），但从冻结那一刻起，执行层的每一步都是确定性的。这是"模型提议、人审拍板、引擎执行"三权分立的执行侧落地。

### 6.5 为什么 QA 基线是控制面记录，而不是 Agent 自己声明的？

每个工作包物化时，平台在冻结基线上预生成一份 QA 基线记录（worktree 路径、基线 commit 等）。Agent 报告"QA 过了"时，平台对照这份记录机械核验（**核验真实改动**），**报告值永远不作为证据**。这是 overnight 实弹暴露的"假 done_success"类缺陷的系统性根治。

### 6.6 为什么重试预算是 2，写死在平台侧？

retry-fail-retry 死循环烧的是真金白银的沙箱。人保留点击权（每次重试都是人点的），但预算封顶让循环必然终止。2 次是实弹经验值：偶发故障重试一次足够，第二次还失败基本是系统性问题，该 defer 或重新拆分了。

### 6.7 为什么取消要级联？

根任务取消时：所有未终结的子任务 → cancelled，所有分支实例 → cancelled，根 run → cancelled，审计留痕。**已终结的子任务不动**（done_success 的成果是既成事实）。没有级联的取消会留下"僵尸分支"继续烧容器。

### 6.8 为什么 reconciler 是"自动重发 + 只告警不杀"两级？

- **Tier 1（自动）**：workflow run 卡住 >15 分钟 + 活跃步是 Agent 步 + 没有运行中的容器执行 → 自动重新触发。这治的是"事件丢了"——补一次事件，成本接近零。
- **Tier 2（只告警）**：容器的 runtime run 还挂着 running 但 15 分钟没动静 → 在任务上写"疑似挂起"告警。**不自动杀**，因为"长构建"和"真挂死"从外部不可区分，误杀的代价（丢工作现场）大于等待的代价。挂起治理的完全体需要 Agent 侧心跳，那是下一轮的事。
- **human_review 永不自动推进**——两级都无权替人做决定。

## 7. 实弹验证账本（这些结论不是纸面推导）

三轮 VM 实弹（batch-test1 项目，2026-10-02），全部证据在 kv_records 可取证：

| 验收项 | 实弹证据 |
|---|---|
| 并发闸 + 补激活 | 三轮演练，日志反复出现 `holding back N ready work package(s) behind the concurrency cap (2, …)`；wave0 完成 wave1 自动物化；全程 running ≤ 2 |
| 取消级联 | cancel 根任务 → DB 证实 2 子任务 + 2 分支实例 + 根 run 全部 cancelled |
| 造败→retry/defer | 走真实上报链注入失败 + 1 次真实 Agent 失败；retry 复用子任务身份；预算超限 409（"exhausted its retry budget (2 of 2); defer it or re-plan instead"）；defer 建待办 + 下游自动 deferred；**全部终结后 join 自动放行进集成评审** |
| 挂起两级判据 | Tier1 日志 `re-firing stalled run … idle 15m+` 多次实弹；Tier2 实弹告警 `suspected agent hang` 落任务 summary |

过程中还实弹抓了 4 个预存缺陷并全部修复部署（幽灵脏树导致审批 500、reconciler 空 Branch、Agent 绑定带项目前缀导致派发全 skip、defer 后 stage 永久滞留）——每个都有回归测试。**这套机制是被故障咬过之后长成这样的，不是画出来的。**

## 8. 给审查者的十三个问题（请逐条回答）

**信任与安全**
1. 冻结记录 + digest 是唯一信任锚。有没有我们没想到的路径，能让未冻结的计划被物化？
2. `infra:*` 豁免了需求关联。会不会被滥用——把业务功能包装成 `infra:` 包来逃避验收追溯？
3. Agent 绑定（agentBinding）冻结期只校验非空（§3 已勘误）。解析失败的实际表现是：派发时 trigger 静默 skip（现在会落系统评论 attention，但状态仍停摆），要等人工发现。绑定到"新来的、没上下文的 Agent"则完全不受阻——这两种失败形态哪个更伤？

**并发与一致性**
4. 并发闸默认 2。这个数字对 8 核 16G 的宿主机合理吗？还是应该按内存动态算？
5. 波次补位依赖"分支完成事件"。如果完成事件在进程重启时丢了，reconciler 的 15 分钟兜底是否足够？中间这 15 分钟整个 stage 停摆，可接受吗？
6. 重试复用身份、defer 重戳实例——两个操作并发打到同一个分支实例上，CAS 能兜住吗？（我们用 revision-CAS，但想听攻击思路。）

**语义与边界**
7. deferred 的传染语义：上游 defer，下游自动 deferred。如果下游其实不依赖上游的"结果"、只依赖它的"存在"呢？（例：wp-B 依赖 wp-A 的接口定义，A 缓办后 B 的接口从哪来？）
8. join 对 deferred 放行。如果一个计划 10 个包 defer 了 9 个，集成评审拿到的是 1 个包的成果——这合理吗？要不要"deferred 过半 → 强制重新裁决"的闸？
9. 失败类别（compile_test/business_assertion/environment/unknown）目前是"人选类别、系统推荐"，没有自动分类。这个类别字段现在的实际用途只有留档——它值得存在吗？什么时机值得升级成自动分类？

**产品与流程**
10. preplan 草案不落库。操作者改了半小时的草案，浏览器一崩就没了。这个代价 vs "两份计划谁说了算"的歧义，我们选对了吗？
11. scale_gate 无裁决时 fail-safe 指 linear（降级串行）。为什么不指向"报错让人来裁决"？
12. 重试预算 2 写死平台侧。要不要按包的"风险等级"差异化？
13. 整条链路里人要点击三次确认（需求快审、契约评审、集成评审）。哪一次最可能被橡皮图章化（无脑点批准）？那一次的保护够吗？

## 9. 边界说明（我们明确不做什么）

以下内容是**有意识的范围裁剪**，不是遗漏，审查时请不要当成缺陷：

- L1 自动重试 / 自动失败分类：本轮只做"人选类别、系统推荐"。
- L2 Leader（多 Agent 协调者）：前置条件是本轮机制 + 独立设计评审通过。
- 归档/删除的级联：只有取消级联。
- 挂起自动处置：Tier 2 只告警不杀。
- "等待外部"状态机：在失败类别里留了语义位（environment），状态机本身不做。
