# batch-test2 评审整改方案：从"演示原型"到"可交付工程"的流水线对策

依据：batch-test2 外部对抗式评审（三条致命断裂链 + major 清单），2026-10-08。
回答的核心问题：**我们这条 multigent 流水线，哪个环节容易放行这类问题？以后怎么拦？**

---

## 1. 诊断：缺陷不是 agent "写错了"，是流水线"没问对问题"

三条断裂链逐一归因到流水线环节，结论一致：**评审 agent 的检查项与交付目标之间缺一层"可机判的闸门"**。AI 在没人要求验证的地方，交付的是"看起来能跑"而不是"被证明能跑"。

### 🔴 链 1：信任链断裂（RSA 私钥硬编码 / JWT 硬编码 / 匿名可写 / 永久授权）

| 流水线环节 | 现状 | 为什么放行了 |
|---|---|---|
| 编码 agent | 密钥硬编码进源码 | 任务 prompt 只说"实现签名/授权"，没给"密钥必须外部化"的硬约束 |
| Agent 初审闸门 | reviewer-agent 实测验证功能 | 审的是"功能对不对"，没有安全红线检查项——**评审 prompt 里没有安全清单，评审就不存在** |
| CI | 三 stage（lint/test/build） | 无 secret 扫描步骤，`git grep` 级别的硬编码密钥直接进库 |

**归因**：平台安全红线（AGENTS.md §7 第 3 条"无硬编码密钥"）在 batch-test2 的模板 AGENTS.md 里只有一句话，没有机判工具兜底。AI 对"约定"的遵守率远低于对"闸门"的遵守率。

### 🔴 链 2：持久化断裂（7 repository 不落库 / 6 表 5 空 / 重启失忆）

| 流水线环节 | 现状 | 为什么放行了 |
|---|---|---|
| 编码 agent | repository 写了、表建了、但写入路径没接 | 每个单元测试各自 mock，集成缝没人看 |
| Agent 初审 | 实测验证 = 调 API 看返回 | API 返回 200 不代表落库——**单进程内存验证永远是"重启失忆"盲区** |
| CI/测试 | 155 测试"属实" | 测试金字塔全是 mock 单测，零持久化断言（Testcontainers 评审方补测才暴露） |
| 人工审核节点 | approve 时看什么？ | 无结构化验收清单，人审退化成看 UI 演示 |

**归因**：fu91es 模板初始态是 in-memory repository，升级到 DB 是 agent 临场发挥（模板 1.2.0 已修——升级路径三步走写进 architecture.md §4）。但更本质的是：**没有任何环节要求"重启后数据还在"这条断言**。

### 🔴 链 3：端到端断裂（通信密钥随机生成不下发 / SDK 无心跳编排 / 注册 100% 被拒）

| 流水线环节 | 现状 | 为什么放行了 |
|---|---|---|
| 任务拆分（W2 拆分器） | 按模块拆（服务端/SDK/文档） | **跨模块契约（密钥格式、心跳协议、注册流程）没有显式物化**，每个 agent 对"另一端"的想象各自成立 |
| contract/ 契约 | 无（模板 1.2.0 前不存在） | 拆分后三个 agent 三套隐式假设，集成必然 404 |
| join/集成评审 | touched_paths 双向闸门 | 只验证"没改别人的文件"，不验证"两边真的能对上" |

**归因**：这是 multigent 自己也发生过的问题（defect #16 解锁未修码、语义缺陷轮的 sharedContract）。大需求拆分后，**模块间协议是最高风险产物，但它恰恰不在任何闸门的检查面上**。

## 2. 整改方案（按投入产出排序，四层防线）

### 第一层：模板层（已完成——本轮 1.2.0 直接消灭链 2 的"临场发挥"）

- ✅ 持久层升级路径三步走写进模板（architecture.md §4 + application-db.yml + V1__init.sql）——agent 不再自己发明 H2 配置。
- ✅ contract/ 冻结契约目录 + 变更控制——链 3 的跨模块协议有了显式落点。
- ✅ AGENTS.md 安全默认值条款（§7.5：不得硬编码密钥/永不过期令牌/匿名可写端点）——链 1 有了文字依据。
- ⏳ **待补**：seed 模板时同步给编码 agent 的 prompt 里注入"AGENTS.md §7.5 安全红线违反即返工"的提示（模板文字 → prompt 注入的接线，平台侧小改）。

### 第二层：评审闸门层（核心增量——把"安全与持久化"变成机判清单）

评审 agent 的 prompt 从"审功能"升级为"审功能 + 过四张确定性清单"：

1. **Secret 扫描清单**（机判，秒级）：`git diff --staged` 上跑正则（`BEGIN.*PRIVATE KEY`、`secret|password|api[_-]?key\s*=\s*["'][^"']{8,}`），命中即 P0 打回。CI 同款步骤兜底（`.gitlab-ci.yml` 加 `secret-scan` job，模板同步）。
2. **持久化断言清单**（半机判）：存在 repository/repository 变更时，必须回答三问——①写入路径是否真调用了持久层（不是只建表）②集成测试是否有"重启后可读"断言 ③ Flyway 迁移与实体是否同步。三问有一问"否"即打回。
3. **契约一致性清单**（机判）：`contract/api-skeleton.md` 列出的端点集合 vs Controller 实际注解集合——**这就是本轮已落地的 `make docs-check`**，直接推广到所有已实例化项目。
4. **端到端冒烟清单**（半机判）：多模块任务（服务端+SDK+客户端）的集成评审节点，强制要求一条"从模块 A 入口到模块 B 出口"的实弹链路证据（curl/脚本输出贴进评审材料），缺证据即打回。

**落地位置**：`internal/workflow` 模板 `unified-delivery-pipeline` 的 reviewer-agent prompt + 验证步注入。改动面是 prompt/模板文本，不动引擎代码。

### 第三层：验收证据层（防"155 测试属实但全是 mock"）

- **测试构成披露**：交付步在任务评论里强制输出测试构成摘要（单测/集成/端到端各自数量 + 是否存在持久化断言 + 是否存在跨进程断言）。不是限制 mock，而是**让"零集成测试"这个事实在人工审核节点可见**——评审人看到"155 单测 0 集成"自然会要求补。
- **QA 证据真实性**：`make test` 输出原文（含 skipped 数量）贴评论，禁止"74/80 passed"这类自算口径。评审报告实锤的问题（acceptance-spec 明文 skip、IT 从未通过）在披露要求下会自动现形。
- 人工审核节点的 UI 显示该披露块（已有任务评论渲染，零前端改动）。

### 第四层：模板护栏层（把 1.2.0 的新设施变成存量项目的可升级资产）

- `CIBaselineFilesForTemplate` 已支持按模板补种 CI 基线——把 `secret-scan` CI job 与 `scripts/docs-check.mjs` 纳入 CI 基线文件清单，存量项目经"重新实例化/补种"获得闸门，不必等新项目。
- 时机：等第二层清单在 batch-test3 实跑一轮校准后执行，避免闸门误报率未调优就全量铺开。

## 3. 明确不做 / 后续议

- **不做自动安全审计 AI**：第一性原则是确定性优先——正则和路径集合比对能机判的，不交给模型判断。模型只负责"三问"这类需要理解代码意图的半机判项。
- **不做自动修复**：闸门只打回不代改。修复质量仍走 agent/人工，避免闸门变成另一个不可审计的黑盒。
- **挂起检测/超时下线 CAS**（评审报告 major 项）：属 runtime 心跳治理，与本三条断裂链不同层，维持既有 backlog 不并入本轮。

## 4. 验收方式（方案自身如何被验收）

1. batch-test3 立项时：确认 seed 的是 1.2.0 模板（digest 变化），contract/ 与 docs-check 出现在 workspace。
2. 故意让编码 agent 硬编码一个测试密钥：验证第二层清单 1 打回（评审材料含 secret-scan 命中记录）。
3. 故意交付"repository 未接线"实现：验证清单 2 三问打回。
4. 拆一个双模块需求：验证清单 4 端到端证据缺失即打回。
5. 上述任一未生效，回滚对应 prompt 注入，缺陷登记。
