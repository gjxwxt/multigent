## 1. 为什么会有这个方案（问题起源）

### 1.1 事实起点

Multigent 的 greenfield 交付流水线（`greenfield-delivery-pipeline`）在需求澄清之后设有 **OpenDesign 设计确认闸门**（design_review，human_review 类型）：平台把已确认需求发给 OD 平台生成高保真 HTML 原型，人在"确认流转"时平台冻结原型 HTML 快照，下游实现编码步以"需求全文 + 冻结快照"双输入开工。

### 1.2 已确认的缺口（本方案的存在理由）

**原型与需求之间的增量没有仲裁机制。** 具体场景：用户在 OD 画布上迭代原型时，可能加入需求文本里不存在的东西（"感觉这里可以加个按钮"），或者 Agent 在生成原型时自行发挥了需求外的元素；反过来，需求要求的某个功能原型也可能漏画。确认流转时：

- 平台不检查原型与需求的差异——冻结的是"你点头那一刻的 HTML"，无论里面有什么、缺什么；
- 实现步同时拿到需求（行为契约）和原型（视觉基线），**原型里多出来的 UI 结构大概率被跟着实现**（视觉基线效力），但其行为语义没有任何规格定义；需求里有而原型漏画的，实现 agent 以谁为准同样不可预测；
- 该 delta 处于无规格状态：QA 的验收测试规格（test_spec_manifest）不会覆盖它，Agent 初审的 design_conformance 只评估"实现 vs 原型"一致性，不评估"原型 vs 需求"一致性；
- 唯一的消解手段是确认人**自觉**在 approve comments 里写差异说明——依赖人的记忆与自觉，没有流程强制。

一句话：**双向二义性真实存在，且当前完全靠人肉闭环。**

### 1.3 为什么说"大概率被跟着实现"而不是必然

实现步 prompt 把需求描述为行为目标（TDD 依据 test_spec_manifest），把设计产物描述为"参考"。Agent 的实际取舍不可预测——可能跟原型走（视觉基线），也可能因无测试目标而忽略。**正是这种不可预测性本身是问题**：同一份输入，两次交付可能一个实现了一个没实现，且没有任何环节会显式暴露这个分叉。

## 2. 真实需求（提出人原话与意图转译）

提出人原话（2026-10-04，五轮反馈已全部吸收）：

> 当我们实现原型设计之后，回到平台点击"确认流转"时，应该加一层 Agent 校验层：拿到 OD 里相关项目的 Agent 对话中人的输入会话历史、HTML、以及需求，以这几个为基准，判断新增了什么东西。弹出一个弹窗与人交互，把当前原型与需求的二义性展示出来，供他裁决。裁决作为下游的一部分传递下去。
>
> 而且这种裁决方式甚至可以体现在其他方面，比如需求澄清部分，让 Agent 主动问问题，也可以通过这种弹窗的形式。

意图转译（评审者请按此校准，发现偏差请指出）：

1. **核心诉求**：把"人凭记忆找差异"变成"Agent 先做差异审计、人只做裁决"——人在环流程里人应该做判断决策，不该做找不同的苦活；
2. **裁决要物化**：不是聊完就丢，而是作为步骤输出字段冻结、随流水线下行，ATD 和实现步都能消费；
3. **形态要通用**：差异审计只是第一个应用；"Agent 主动提问 → 弹窗 → 人作答 → 答案回填步骤输入"应是平台级交互原语，可复用于需求澄清等问题澄清场景；
4. **OD 弹窗职责纯粹**（第二轮裁定）：OD 弹窗只承载设计内容的展示与迭代，裁决是点击流转之后的独立环节；
5. **诚实性优先**（第三轮裁定）：人不必替 Agent 的判断背书——不确定的判断用"跳过"显式推迟，而不是被迫三选一站队；
6. **差异用双侧对照呈现**（第四轮裁定）：有/无是相对的，展示需求侧与原型侧各自的"有/无"与理解陈述；
7. **打回不重裁**（第五轮裁定）：打回设计后的重新审计必须自动沿用已裁决项，只裁新增/失效项；
8. **界面克制**（第六轮裁定）：不做装饰性徽标/图标/彩色状态，不展示审计元信息行，不做手动添加差异入口，操作按钮固定在卡片右下。

## 3. 真实交互场景（方案落点在哪里）

以当前实际操作流为准（batch-test2 项目 t-20261003-hdspz4 实录）：

1. 用户在任务 follow 页点击"选择设计方案"，打开 DesignReviewModal（内嵌 OD studio iframe）；
2. 原型就绪后，用户在 iframe 内查看/迭代原型，可能通过 OD 聊天让 Agent 改原型（这些聊天输入留在 OD 侧）；
3. 用户点**「校验并确认流转」**→ 平台抓取当前 HTML + 会话历史 → 审计 → **弹出独立裁决弹窗** → 逐条裁决 → 裁决完成确认 → **冻结审计时抓取的那份 HTML**（同源冻结，非重抓，见 §5.3 末）+ 裁决同事务落库 → 流转到 scale_gate。

**注入点在第 3 步内部**：用户在第二个弹窗点下确认的那一刻，心智是"我为这份裁决过的东西签字"。

## 4. 备选交互形态与取舍

评审者请重点审这一节：这里的选择决定了方案的边界。

### 形态 A：独立流水线节点（design_delta_audit，agent_task，人审两次）— 否决

流水线拓扑变了（存量定义需模板升级）；连续两次人审（裁决节点 + 确认节点），用户疲劳；"审计"和"确认"拆成两个页面两个时间点，用户裁决时看到的原型可能已又被改过，裁决与快照错位。

### 形态 B：纯后端校验（无弹窗，差异直接写进字段，不问人）— 否决

差异的**裁决权**在人——"这个按钮要还是不要"是产品决策，Agent 无权代答；默认纳入等于把无规格实现合法化，默认剔除等于悄悄丢掉用户在 OD 里亲自要过的东西。跳过人的裁决，方案退化为自动猜测。

### 形态 C（选定）：两段式确认——确认动作触发审计，独立裁决弹窗

- OD 弹窗保持纯粹（iframe + 打回/刷新），**不内嵌任何裁决 UI**；
- 点「校验并确认流转」→ 平台原子执行"抓取 HTML+会话 → 审计 → 返回差异报告（HTML 内容连同其 hash 一并返回前端暂存）"（前端分阶段加载态）→ **弹出独立的裁决弹窗**逐条裁决 → 全部处置完成 → 确认按钮点亮 → 二次点击真正提交（**冻结审计时抓取的那份 HTML（同源冻结，不重抓）** + 裁决同事务落库）→ 流转；
- **选定理由**：职责分离（看/改设计与裁决差异是两种心智，不塞同一容器）；**审计对象=冻结对象**（冻结的就是审计时那份 HTML，同源冻结使两者构造性一致，无需过期比对机制；注意这不是"确认时刻的最新 HTML"——若用户裁决期间又回 OD 改了原型，改动不在本次裁决范围内，落库时 UI 明示抓取时间点，详见 §5.3 末与 §6.3）；无白跑（每次审计必然被消费）；零流水线拓扑变更。
- **代价与对策**：确认从"一次点击"变成"点击→等待→裁决→再点击"。对策：加载态分阶段明示（正在抓取原型 → 正在读取设计会话 → Agent 审计中），首击文案"校验并确认流转"把等待变成可理解的流程；审计失败/超时给"重试"与"审计未完成仍要确认（留痕）"两条逃生门（§6.7）。

### 形态 D：实时增量捕获（OD 聊天每轮结束后即时标记）— 否决

需要 OD 逐轮回调或逐轮拉取（现无此接口，同 §5.1 基准 B 的接口缺口；即使候选 1 的只读端点落地，也只能事后拉取而非逐轮推送）；实时链路中断即漏记；澄清过程中的"加"可能是反复试探，最终留在原型里的才算数——确认时一次性对账更可靠。

### 形态 E（v1 曾选定，被提出人否决）：OD 弹窗内嵌裁决 tab + ready 预跑

提出人裁定 OD 弹窗应专门展示 OD 内容；预跑引入过期重跑整套复杂度而两段式构造性免除。保留供评审对照——若评审认为"确认零等待"价值大于职责分离，可复议。

## 5. 方案设计（形态 C 展开，最终形态）

### 5.1 审计输入与判定基准

| 输入 | 来源 | 可得性 | 用途 |
|---|---|---|---|
| 需求全文 | design_review 步输入 `approved_requirement` | **现成**（步骤输入字段） | 判定基准 A（行为/功能范围） |
| 待冻结 HTML | OD `ListProjectFiles/GetProjectFile`（与快照同一抓取链路） | **现成**（现有 odClient 接口） | 被审对象 |
| OD 会话中**人的输入** | 无现成接口，**条件性可用**（见下） | **待补** | 判定基准 B（人的显式意图来源） |

**判定基准 B 的可得性（v2.5 修正，外部预评审 P0）**：

平台与 OD 之间是纯 HTTP 连接（`designConnectionConfig` 只有 BaseURL/APIKey/ConnID），odClient 现有 7 个方法（ListProjects/CreateProject/StartRun/LatestRunStatus/DeleteProject/ListProjectFiles/GetProjectFile）**没有任何会话内容回读接口**；平台对一次设计只持有 conversationID（StartRun 返回值），之后用户在 OD 里说什么，平台当前一条都不知道。整理人曾在 OD 容器内直连其 SQLite 取证读到 `messages` 表（role/content 齐全，含平台注入的【角色与使命】首条，可精确排除）——**但这只是取证通道，不是生产可用路径**（跨容器 DB 直连违反部署边界，且 OD 升级可能改表结构）。外部评审对"已实弹验证可直读"表述的批判成立，v2.4 及之前版本的该表述有误，本版已改。

**基准 B 的补齐路径（一期前置任务，非阻塞项）**——两个候选按优先级：

1. **OD HTTP API 扩展（首选）**：请求 OD 侧增加只读端点 `GET /api/projects/:id/conversation`（按 conversationId 返回 role+content 列表，鉴权复用现有 OD_API_TOKEN）。OD 是自部署容器，改造成本可控；接口面窄（只读、不暴露 DB 路径）；
2. **平台侧记录**：平台在 design/start 时把自己注入的首条 prompt 存入任务上下文；用户在 OD 内的后续输入仍拿不到——**此路只解决"排除平台注入"不解决"拿到人的输入"**，只能作为候选 1 失败后的部分降级。

**降级声明（候选 1 未落地或调用失败时，方案仍成立但能力收缩）**：

- `source_class` 四分类**全部退化为 uncertain**；
- §2 意图 1 的"裁决负担从 N 条降到只细看拿不准的几条"**不成立**，每条差异都需细看；
- 默认倾向（§5.3）、意图新旧信号与偏离类默认建议（§5.3.1）**失去依据，不展示默认建议**；
- schema 的 `source_class`/`source_evidence` 字段保留但填 uncertain/空；
- 审计退化为**纯 HTML vs 需求对照**——差异发现（新增/缺失/偏离三类）不依赖会话历史，**核心价值保住，损失的是来源分层与默认建议**。

**会话历史可得时的用法**（对每个疑似差异元素判断来源）：

- **用户亲口要的**（OD 聊天里人说"这里加个 XX"，Agent 执行了）：事实意图，裁决默认倾向"纳入需求"（仍需人确认，备注草稿预填）；
- **Agent 自行发挥的**（会话里无对应人的输入）：最需要裁决的一类，默认倾向"不纳入需求"；
- **需求文本有但表述不同的**（措辞漂移，非真新增）：倾向提示为低风险；
- **来源不确定**（会话历史不完整/用户在平台外改文件）：如实标 uncertain，不猜。

来源分类把人的裁决负担从 N 条降到"只细看拿不准的那几条"——**此收益以基准 B 补齐为前提，评审请按此条件审查**。

### 5.3 裁决 UI（两段式：确认动作触发的独立弹窗）

**触发链**：OD 弹窗点「校验并确认流转」→ POST design/audit-delta（新端点：抓取 HTML+会话 → 模型审计）→ 前端弹**独立裁决弹窗**：

- **加载态分阶段**："正在抓取原型… → 正在读取设计会话… → Agent 审计中…"；
- **差异分组**：「原型新增（需求里没有的东西）」与「原型缺失（需求要求但原型未体现）」两组，组头带计数；
- **裁决按钮（新增类）**：
  - **纳入需求**：该元素进入需求口径；备注可选（渐进披露，见下）——写则进 ATD 转 Case，不写则由 ATD 按元素可见行为自行规格化；
  - **不纳入需求**：该元素不进入需求口径；备注可选。实现步收到的是"原型中有此元素、但明确不实现"的禁区声明；
  - **跳过**（诚实性关键设计）：
    - **不做断言**：不说有差异也不说无差异，仅"本条暂不裁决"——人不必替 Agent 的判断背书；
    - **后果明示**：点击即显示——不生成测试用例、不写入实现规格，以"未裁决"状态随快照下传；
    - **初审回流**：Agent 初审核对跳过项——若发现它被实现了（代码即事实），在 design_conformance 中标注并交人工代码审核**再次裁决**，届时人看到的是真实实现而非原型推测。跳过不是变相批准也不是变相剔除，是**把裁决推迟到证据更强的环节**；
- **裁决按钮（缺失类）**：
  - **打回设计补齐**：闭环见 §5.3.1；
  - **本次豁免**：该需求点本轮不做（语义同"不纳入"），备注留痕；实现步若擅自实现判缺陷；
  - **跳过**：同上跳过语义；
- **备注渐进披露**：默认无输入框；选中"纳入/不纳入"后卡片右下角出现「添加备注（可选）」，点击才展开文本框（Agent 的 suggested_spec 仅作草稿预填）；
- 全部条目处置完毕（跳过也算已处置），"确认流转"才可点 → 二次提交：**冻结审计时抓取的那份 HTML（同源冻结，不重抓）** + 裁决落库**同事务**；
- **同源冻结契约（v2.6 补，外部预评审 P0-B）**：审计首击抓到的 HTML 连同其 sha256 一起返回前端暂存；二次提交冻结的就是这份内容（服务端收到 decisions 时一并收到暂存 HTML+hash，落库前对回传内容重算 hash 并与首击 hash 比对；hash 于首击抓取时由服务端计算并随内容返回——该校验防传输损坏与前端状态错乱，非对抗恶意客户端的防线，前端为第一方代码）。**理由**：首击抓取与二次提交之间隔着整个裁决过程（数分钟级），期间 OD Agent 可能仍在写文件——若二次提交重新抓取，裁决针对的是 v1、冻结的却是 v2，正好复刻 §4 否决形态 A 的"裁决与快照错位"，且差分复审的元素指纹全部锚在被审那份上，重抓会使所有已裁指纹失配。同源冻结少一次抓取、且审计/裁决/冻结三者天然一致；
- **代价的诚实披露**：同源冻结意味着冻结的不是"确认时刻的最新 HTML"。若用户裁决期间又回 OD 改了原型，改动不在本次裁决范围内——裁决弹窗底部明示"本次裁决针对 HH:MM 抓取的原型"；用户若改过原型应重击校验（重走审计，已裁决项走差分复审沿用判定，不重裁）。审计摘要记录抓取时间戳与 hash，下游可追溯；
- **零差异分支**：审计结果 0 条时不弹完整裁决面板，给轻量确认条（"Agent 未发现差异，确认流转？"一键确认）——审计摘要与 `design_delta_decisions=empty` 照常落库，不静默；
- **逃生门**：审计失败/超时提供"重试"与"审计未完成仍要确认"（后者 `audit_status=incomplete` 留痕，见 §6.7）。

- **裁决按钮（偏离类，v2.4：双侧都有但描述/参数不一致）**：

  **一期范围裁定（v2.6，消融结论）**：偏离类是三类中检测最易误报的（措辞漂移 vs 真偏离难分——参数级对照会把"需求写 90 天、原型恰好也画了 90 天选项但表述不同"判成偏离）、UI 最重的（侧卡单选 + 另定行为备注必填）、验证最少的（v2.4 才加入）、默认建议还依赖条件性可用的 intent_signal（§5.1）。**一期降级为"只读提示 + 跳过"**：审计仍检测并展示双侧对照（价值在于让人看见不一致），但不提供权威侧单选/另定行为交互——用户认为需要处理时用「跳过」+ 备注（备注自由填写，等效"另定行为"的记录功能），需要改原型则走打回。侧卡单选等完整交互**推二期**，与 §5.5 原语化一并做。以下 v2.4 原设计保留供二期实现参照：

  - **冲突不可用三按钮消解**：双方都"有"，"纳入需求"纳不进（两侧各有版本），"不纳入需求"更不通（需求明明有）——需要的是**权威侧选择**，不是二值取舍；
  - **交互形态：侧卡单选**（提出人提议，整理人认同并采纳）：点击需求侧卡或原型侧卡即选中（高亮），**替代独立按钮**——选项就是两侧卡片本身，所见即所选；右下角保留「另定行为」与「跳过」两个小按钮兜底；
  - **「另定行为」**：两侧描述都不对（比如需求写的是老交互、原型改的也不完整），备注**必填**，给出真实预期行为；
  - **「跳过」**：同全局跳过语义（暂不裁决，初审回流）；
  - **检测方式**：审计对双侧 reading 做**参数级对照**（数量、阈值、交互方式、状态枚举），发现不一致即产出偏离类条目——如需求"保留最近 90 天审计日志"vs 原型下拉框只有 30/60/180 天；
  - **默认建议带意图新旧信号**：原型侧的版本若产生自**需求定稿之后**的 OD 会话编辑（会话时间戳 > 需求评审通过时间，且是你亲口要的改动），倾向建议"以原型为准"（更新的意图）；原型侧是首版生成、无会话轨迹的，倾向"以需求为准"（需求经过评审，权威性更高）。此为默认建议，选择权在人。

### 5.3.1 「打回设计补齐」的闭环：续聊式打回 + 差分复审

**提出人推演的流程是成立的，也是本设计的约束**：打回到设计 = 向**同一个 OD 会话**追加一条补齐消息（"需求 §目标 2 要求配额实时视图，请在原型中补齐"）。**地基假设（外部预评审 P1-1）**：Agent 在既有上下文上继续改原型——**不是重新生成**。此假设尚未实弹验证：OD 的 OpenCode 收到补齐消息后，可能整页重生成 HTML（LLM 无增量编辑保证），届时 element_fingerprint 大面积失配 → 已裁决项被误判"元素已消失"全部重弹 → "每轮负担单调递减"反转为"越打回越多"的爆炸。**一期开工前必须先做探测**：向真实 OD 会话追加一条补齐消息，对比前后 HTML 的 diff 形态（增量 patch vs 整页重写）：

- **增量修改** → 差分复审按 §5.3.1 机制直接成立；
- **整页重生成** → 指纹策略升级为**语义匹配**（不做字节/结构指纹，改由审计模型对"上轮已裁元素清单 vs 新 HTML"做语义定位，模型能力足以容忍 DOM 重排——成本是每次重审多一次模型侧对照，但 correctness 依赖模型而非脆弱的字节指纹；失配兜底仍是失效重裁，错在多问不在漏问）；
- 两种结果都不推翻差分复审框架，只决定指纹层的实现形态——但必须在规格定稿前实测，不能带着未验证假设送审。

后续机制在新一轮审计语境下裁定如下：

**差分复审（differential re-audit），已裁决项永不重新裁决。** 三层机制：

1. **上轮裁决的沿用（元素指纹匹配）**：审计 prompt 携带上轮差异条目及裁决结果。对每个上轮"纳入/不纳入"的元素，先在新原型 HTML 中定位对应元素（**指纹层一期先做最简版：元素文本 + 稳定选择器**（v2.6 消融裁定——语义匹配等地基假设实测后再决定是否上，避免一期过度设计）；无论哪种均不依赖位置索引——补齐会导致 DOM 平移）。找到且用户上轮已裁决 → **裁决自动沿用**，本轮不再弹出；
2. **失效重裁（仅两种情况）**：a) 指纹找不到（元素被 Agent 改掉/删掉）→ 标记"原元素已不存在"，重新弹出裁决（裁决对象变了）；b) 元素在但语义明显变化（Agent 理解陈述与上轮不一致）→ 弹出并标注"与上轮裁决时相比有变化"，附上轮裁决供参照。**除此之外没有任何路径让已裁决项回到待裁状态**——机制保证而非靠用户自觉；
3. **闭环追踪（打回项）**：上轮"打回补齐"的条目本轮重点核对——原型中该缺口是否已补上。补上了 → 转"已补齐"只读展示（不需再裁，补齐的内容就是需求里已有的东西）；仍未补上 → 重新弹出裁决。

**确认弹窗信息架构**：顶部**默认收起的"上轮裁决（N 项）"折叠区**——每条带系统判定的状态徽标（已沿用 / 已失效重裁 / 已闭环），只读仅供参考；**主区只列本轮需要处置的条目**（新发现差异 + 失效重裁 + 打回未闭环），确认按钮只解锁这些条目。用户不承担"已解决还是没解决"的判断负担——系统先分好。

**成本与收敛**：差分复审的审计 prompt 多携带上轮上下文，输出只有差分，token 成本与首轮相当或略低；打回在裁决弹窗内允许多条勾选一次打回（合并为一条补齐消息），每次打回任务评论留痕；不设次数硬闸（设计迭代本需多轮），沿用机制保证每轮用户负担单调递减，不存在"越打回越多要重裁"的爆炸。

### 5.4 下游消费（"commit 传下去"的落地）

裁决结果物化为 design_review 步两个新输出字段，与 HTML 快照（`approved_design_snapshot_path`）在同一确认请求落库，永不错位：

- `design_delta_report`：审计差异条目（§5.2 schema 数组）；
- `design_delta_decisions`：逐条裁决（delta_id → action + 可选备注 + audit_status）+ **审计摘要**（总条数、各 action 计数、抓取时间戳与 hash）；
- **跳过可观测性（v2.6 补，消融结论）**：§8 问题 8（大量跳过会不会压垮人工代码审核）的回答——审计摘要记 skipped 计数并在超阈值（建议 ≥5 或跳过占比过半）时在裁决弹窗顶部提示"N 项暂不裁决，将在初审对照实现情况"；初审回流的人审压力因此可观测——若实弹中跳过占比持续走高，说明审计质量或 UI 引导有问题，而非静默累积。

| 下游 | 消费方式 |
|---|---|
| ATD（验收测试设计） | "纳入"项（有备注按备注、无备注按元素可见行为）转化为补充 Case 来源（ac_id 标注 design_delta，便于追溯）；"不纳入/豁免"与"跳过"项不生成 Case；"打回补齐"项在新一轮审计后重走裁决 |
| 实现步 | prompt 输入显式携带：纳入项=有规格的功能；不纳入项=**明确禁区**（原型里有但不许实现）——直接消解 §1.3 的不可预测性；跳过项=未规格化，不引导实现也不禁止 |
| Agent 初审（self_review） | design_conformance 对照裁决清单：实现了"不纳入/豁免"项=缺陷；"纳入"项未实现=缺陷；**"跳过"项若被实现→标注后回流人工代码审核再次裁决**（§5.3） |
| QA | "不纳入/豁免"项若出现在实现中，矩阵判 failed（evidence 引用裁决）；"跳过"项被实现的，引用初审标注 |
| 人工代码审核 | 证据页可查看完整差异裁决记录；跳过项的实现情况在此获得最终裁决（此时有真实代码可看） |

### 5.5 平台通用化（二期）：交互裁决原语

平台已有 `interaction_requests` 全生命周期存储（`db.go:903`：Title/Body/SchemaJSON 表单 schema/SubmissionJSON 回填/ExpiresAt），当前服务 IM 卡片交互。二期把同一原语扩展到控制台弹窗：

- 渲染端：控制台 Modal 组件，按 SchemaJSON 渲染表单/选项，提交回填 SubmissionJSON；
- workflow 侧：agent 步可声明"产出待答交互"（如需求澄清步的待澄清问题结构化），平台生成 interaction_request，人工节点/收件箱呈现弹窗；
- 答案经 edge mapping 回填下游输入——与 §5.4 同构。

需求澄清步现况：Agent 输出"待澄清问题"是纯文本躺在需求草稿里，人读草稿自己找问题回答。结构化成弹窗问答后答案直接回填步骤输入。**此为二期，先验证一期交互形态再抽原语。**

## 6. 已知问题与风险（评审请逐条挑战）

### 6.1 审计质量是启发式的（最重要的一条）

Agent 审计会**漏报**（HTML 里需求外的元素没被识别——例如行为藏在 JS 交互里而非静态结构）和**误报**（把需求内的措辞漂移判成新增）。缓解：UI 明示"Agent 认为的差异，供你裁决，非完整清单"；跳过语义 + 初审回流兜底（§5.3）。**已按提出人裁定不设"手动添加差异项"入口**——漏报的残余风险由初审回流承接。**残留风险**：漏报的差异仍然无规格流下去——本方案降低但不能消灭二义性，UI 与文档必须如实传达，不能让用户形成"审过=没差异"的错觉。

### 6.2 会话历史判"来源"依赖 OD 侧数据可得性

基准 B 当前**条件性可用**（详见 §5.1）：odClient 现无会话回读接口，容器内 SQLite 直读只是取证通道、不是生产路径（跨容器 DB 直连违反部署边界，且 OD 升级可能改表结构）。补齐路径（OD 只读端点扩展）未落地前：source_class 一律 uncertain（fail-closed，降级为纯 HTML vs 需求审计，方案仍可用但少了来源分层）；用户在 OD 用平台外手段（直接改文件）编辑无会话痕，同样落 uncertain。

### 6.3 审计延迟

两段式消除了预跑的整套过期检测复杂度，代价是点「校验并确认流转」后需等待审计完成（数秒到数十秒，一次模型调用）。对策：分阶段加载态 + 首击文案 + 同源冻结（§5.3：审计时那份 HTML 直通冻结，裁决期间原型再被改也不产生错位，落库 UI 明示抓取时间点）。若实弹后普遍反映等待不可接受，复议方向是把抓取（快、确定性）前置到 ready，仅把模型审计留在确认时——前置抓取与冻结对象的一致性同样靠 hash 校验兜底，属部分回退到形态 E。

### 6.4 模型路由依赖

审计调用走设计 agent 的模型链路。已知坑（2026-10-03/04 实录）：OD BYOK 输出硬顶 16,384 tokens，裸名 `glm-5.3-flash` 路由会把预算烧满思考致空响应。审计 prompt 输出是结构化 JSON（短），风险低于原型生成，但**必须走 Fusion/ 前缀或 agent 绑定路由**，禁止默认裸名。这也是待拍板项 `odDefaultModel`（od_client.go:30）修改的另一个理由。

### 6.5 裁决的效力边界

裁决物化后，"不纳入"在实现步是明确禁区——但**没有技术强制**（不是平台闸门拦截，靠 prompt 约束 + self_review/QA 对照）。外部预评审 P1-3 的提醒成立：Agent 自述不可信（平台已有假 done_success 教训），实现步想实现禁区元素仍可能实现，且 self_review 的对照本身也是 Agent 行为。如实登记：**裁决是规格级约束，不是运行时强制**；若要硬闸（实现 diff 触碰禁区元素即 fail），需要 UI 结构到代码元素的映射，当前不现实。**因此一期验收断言只写可测的**（见 §9）："禁区未被实现"不可作为验收断言（测不了、会躺一个永远过不了的项），替代为**可追溯性断言**：裁决记录落库、ATD/实现步输入含裁决内容、self_review 输出的 design_conformance 引用了裁决清单、QA 矩阵对"不纳入项被实现"场景能产出 failed 项（构造一次故意违规来验证检测链路，而非验证禁区本身不可被违反）。

### 6.6 存量任务兼容与模板重新实例化

design_review 步新增输出字段是可选字段，老定义/进行中任务不受影响（字段缺省即无审计，走现状）。确认弹窗改动在前端，随部署生效，无迁移债。

**模板生效路径（v2.5 补，外部预评审 P1-2）**：按工作流双层体系（AGENTS.md §6），模板改动不会自动作用于已落库的定义——greenfield 模板加两个输出字段后，**已实例化的存量 workflow 定义需要重新实例化才能在 UI/引擎生效**。现有启动收敛点 `ensurePlatformWorkflowDefinitions`（workflow_handlers.go:1959）已具备"版本 bump → 存量定义自动升级"的契约（画布 v2 修复已实证该路径），本方案的字段新增应走同一机制：模板版本 bump + Ensure 升级逻辑，避免产生"重新实例化债"。进行中任务（如 t-20261003-hdspz4 已走到 design_review 之后的）按字段缺省处理，不做回填。

### 6.7 fail-open 的留痕义务与首击零写契约

审计失败/超时时允许"未审计仍确认"（不把人锁死），但必须：输出留痕 `audit_status=incomplete` + 任务评论记录失败原因；ATD/实现/初审的输入里带此标记，使"本次未经差异审计"在下游证据链可见——fail-open 但不静默，防止逃生门变成常态旁路。

**首击零写契约（v2.5 补，外部预评审 P2）**：两段式把 human_review 从原子动作变成多步会话——首次点「校验并确认流转」发起的审计**必须是只读操作**（抓 HTML + 拉会话 + 模型审计，全部零写入；快照与裁决只在二次提交时落库）。若首击就冻结快照，用户中途"返回设计继续改"会造成快照与最终确认内容错位。**实现规格必须钉死**：design/audit-delta 端点无任何 DB 写与文件写副作用，幂等可重放（重复点击不产生重复状态）；以端点代码审查 + 一次"审计后返回设计再修改再审计"的实弹回归作为该契约的验收。

**同源冻结契约（v2.6 补，外部预评审 P0-B）**：二次提交**不得重新抓取** HTML——冻结对象必须是审计首击抓取的那份（HTML 内容 + sha256 由前端暂存回传，服务端落库前校验 hash 与内容一致）。防的是"裁决针对 v1、冻结的是 v2"的错位（首击与二次提交间隔数分钟，OD Agent 可能仍在写文件），同时保住差分复审元素指纹的有效性（指纹锚在被审那份上）。验收：实弹一次"审计后继续让 OD Agent 改原型再确认"，断言冻结快照的 hash 与审计首击抓取的 hash 一致、与最终 OD 侧文件不一致。

## 8. 评审关注清单（给评审 Agent 的显式问题）

1. §4 备选形态取舍是否成立？特别是两段式 vs 形态 E（预跑零等待）——若你们判断等待成本不可接受，给出量化依据；
2. §5.2 差异条目 schema 是否缺字段？element_fingerprint 的生成策略（结构+文本+视觉特征多信号？）与失配阈值如何定（§7-8 兜底是失效重裁，错在多问一次不在漏问）；
3. §5.3 缺失判定的边界："需求要求但原型未体现"怎么算体现——元素存在即算还是状态覆盖才算？误报缺失会诱发不必要的打回，判定标准要不要按需求条目粒度分级？
4. §5.3.1 差分复审的沿用判定是否完备？除"指纹失配/语义变化"外是否还有应触发重裁的情况？
5. §5.4 下游消费映射是否有遗漏的下游（brownfield 流水线要不要同步支持，还是先只做 greenfield）？
6. §6.5 "裁决是规格级约束非运行时强制"是否可接受？若不可接受，硬闸的最小可行形态是什么？
7. §6.7 fail-open 留痕是否足以防止逃生门被滥用？"审计未完成仍要确认"要不要加权限或频次约束？
8. 跳过项的回流比例：若大量差异被跳过，初审回流会不会让人工代码审核不堪重负？（v2.6 已给出部分回答：审计摘要记 skipped 计数 + 超阈值提示，见 §5.4——但阈值定多少、提示形态是否足够，仍请评审挑战）
9. 二期原语与现有 interaction_requests 的合并是否有隐藏冲突（IM 卡片渠道与控制台弹窗并存时的路由/去重）？
10. 审计模型调用失败率与重试策略：审计失败逃生门（§6.7）与模型路由稳定性（§6.4）叠加后的预期可用性是否达标？

## 9. 实施边界（一期预估，供排期参考）

- 后端：审计服务（OD 文件+会话历史抓取 → 模型审计 → design_delta_report + HTML/sha256 同源回传）、design/audit-delta 端点、confirm 端点扩展（decisions + 暂存 HTML 落库，hash 校验）、2 个新输出字段 + 模板文本（中英）；
- 前端：DesignReviewModal 确认链改造（两段式：确认→审计加载→独立裁决弹窗→二次提交）、差分复审沿用/失效/闭环状态渲染、上轮裁决折叠区；偏离类一期只读展示（无侧卡单选交互）；
- 不动：流水线拓扑、快照机制本身、OD 侧任何代码；
- 验收（可测断言口径，见 §6.5）：实弹走一遍 batch-test2 任务设计闸门，构造差异各至少一条（新增 / 同义改写 / 原型缺失 / 双侧偏离），验证：审计差异落库、裁决落库、ATD/实现步输入含裁决内容、跳过项初审回流、构造一次"禁区被故意实现"验证 self_review/QA 检测链路能产出 failed 项。**前置探测两项（P0/P1 修正，半天级）**：a) OD 会话回读接口可行性确认（有接口则写明接口名与字段，无则一期按降级声明执行）；b) 打回补齐实测一次（增量修改 vs 整页重生成，决定指纹层实现形态）。
